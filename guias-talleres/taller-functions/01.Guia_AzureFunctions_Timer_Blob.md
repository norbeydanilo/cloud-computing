# Timer Trigger y Blob Storage Trigger con Azure Functions
## Automatizar tareas programadas y reaccionar a archivos en la nube

**Computación en la nube**

---

## ¿Qué vamos a ver?

En la guía anterior creamos una función con **HTTP trigger**: se ejecuta cuando alguien hace una petición web. En esta guía vemos dos triggers adicionales que amplían el concepto de evento:

- **Timer trigger:** la función se ejecuta automáticamente según un horario definido, sin que nadie la llame. Es el equivalente serverless de un cron job.
- **Blob Storage trigger:** la función se ejecuta automáticamente cuando se sube o modifica un archivo en Azure Blob Storage. No hay que consultar si hay archivos nuevos: Azure lo detecta y dispara el código.

Ambos demuestran que Serverless no es solo una API: es código que reacciona a cualquier tipo de evento, no solo peticiones HTTP.

---

## Parte 1: Timer Trigger

### 1.1 ¿Qué es un Timer Trigger?

Un Timer trigger ejecuta la función según una expresión de tiempo definida al crearla. Casos de uso típicos:

- Enviar un reporte cada lunes a las 8 AM
- Limpiar registros antiguos de la base de datos cada medianoche
- Verificar el estado de un servicio externo cada 5 minutos
- Generar backups automáticos a una hora fija

El código se activa solo, sin intervención humana, y vuelve a dormir hasta el próximo disparo.

### 1.2 El formato NCRONTAB

Azure Functions usa expresiones **NCRONTAB** de 6 campos (a diferencia del cron estándar de Linux que tiene 5). El campo adicional al inicio controla los segundos:

```
{segundo} {minuto} {hora} {día-del-mes} {mes} {día-de-la-semana}
```

| Expresión | Significado |
|---|---|
| `0 */2 * * * *` | Cada 2 minutos (en el segundo 0) |
| `0 * * * * *` | Cada minuto |
| `0 0 8 * * *` | Todos los días a las 8:00 AM |
| `0 0 8 * * 1` | Todos los lunes a las 8:00 AM |
| `0 0 0 1 * *` | El primer día de cada mes a medianoche |
| `0 30 9 * * 1-5` | Lunes a viernes a las 9:30 AM |

> El primer campo es el de segundos. Si no se necesita precisión de segundos, siempre se pone `0` ahí.

Para esta guía usaremos `0 */2 * * * *` (cada 2 minutos) para ver la función ejecutarse rápidamente durante la sesión.

### 1.3 Crear la función Timer desde el portal

Dentro de la Function App (`fn-[tu-apellido]-intro`):

1. En el menú lateral, haz clic en **"Funciones"**
2. Haz clic en **"+ Crear"**
3. Haz clic en **"Crear en Azure Portal"**
4. En la lista de plantillas selecciona **"Timer trigger"**
5. Asigna el nombre: `TareasProgramadas`
6. En el campo **"Programación"** escribe: `0 */2 * * * *`
7. Haz clic en **"Crear"**

Haz clic en el nombre `TareasProgramadas` y luego en **"Código y prueba"** en el menú lateral.

### 1.4 El código generado por el portal

El portal genera este código inicial en `index.js`:

```javascript
module.exports = async function (context, myTimer) {
    var timeStamp = new Date().toISOString();

    if (myTimer.isPastDue) {
        context.log('JavaScript is running late!');
    }
    context.log('JavaScript timer trigger function ran!', timeStamp);
};
```

> **¿Qué hace este código?**
> Recibe `myTimer` con información sobre la ejecución. La propiedad `isPastDue` es `true` si la función se ejecutó con retraso respecto al horario programado (puede ocurrir si Azure estaba ocupado). Luego registra en el log el momento exacto de ejecución.

### 1.5 Personalizar el código

Reemplaza el contenido por el siguiente código y haz clic en **"Guardar"**:

```javascript
module.exports = async function (context, myTimer) {
    const ahora = new Date();

    if (myTimer.isPastDue) {
        context.log('La función se ejecutó con retraso respecto al horario programado.');
    }

    // Información sobre esta ejecución
    const info = {
        mensaje: 'Tarea programada ejecutada correctamente.',
        horaEjecucion: ahora.toISOString(),
        proximaEjecucion: myTimer.scheduleStatus ? myTimer.scheduleStatus.next : 'no disponible',
        retraso: myTimer.isPastDue,
    };

    context.log('Tarea programada:', JSON.stringify(info, null, 2));
};
```

> **¿Qué hace esta versión?**
> Construye un objeto con la hora de ejecución, la próxima ejecución programada y si hubo retraso. Lo registra en el log como JSON formateado. No devuelve una respuesta HTTP porque el Timer trigger no tiene cliente esperando: solo escribe en los logs.

### 1.6 Verificar la ejecución en los logs

A diferencia del HTTP trigger, no hay forma de "llamar" al Timer trigger manualmente para probarlo. La función se ejecuta sola según el horario. Para ver que funciona:

1. En la vista **"Código y prueba"**, haz clic en **"Registros"** en la parte inferior de la pantalla
2. Espera hasta el próximo múltiplo de 2 minutos (por ejemplo, si son las 10:03, espera hasta las 10:04)
3. Verás aparecer en los logs las líneas con el mensaje y la hora de ejecución

Los logs se actualizan en tiempo real. Cada 2 minutos aparece una nueva entrada confirmando que la función se ejecutó.

> Si quieres probar sin esperar, puedes cambiar temporalmente la expresión a `0 * * * * *` (cada minuto), guardar, y luego volver al intervalo original.

### 1.7 Cambiar el horario sin tocar el código

El horario de un Timer trigger se define en el archivo `function.json`, no en el código. Para verlo y modificarlo:

1. En la vista "Código y prueba", haz clic en el selector de archivo (donde dice `index.js`) y selecciona `function.json`
2. Verás algo así:

```json
{
  "bindings": [
    {
      "name": "myTimer",
      "type": "timerTrigger",
      "direction": "in",
      "schedule": "0 */2 * * * *"
    }
  ]
}
```

Cambia el valor de `"schedule"` por cualquier expresión NCRONTAB y guarda. El cambio aplica en la siguiente ejecución sin necesidad de redesplegar el código.

## Parte 2: Blob Storage Trigger

### 2.1 ¿Qué es un Blob Storage Trigger?

El Blob Storage trigger ejecuta la función automáticamente cuando se crea o modifica un archivo (blob) en un contenedor de Azure Blob Storage. Casos de uso típicos:

- Procesar una imagen al subirla (redimensionar, clasificar, extraer metadatos)
- Transformar un CSV al cargarlo en el sistema
- Enviar una notificación cuando llega un nuevo archivo de datos
- Validar un documento subido por un usuario

La Function App ya tiene una cuenta de almacenamiento asociada que se creó automáticamente al aprovisionarla. La vamos a usar directamente.

### 2.2 Localizar la cuenta de almacenamiento de la Function App

1. En el portal de Azure, ve al grupo de recursos **`rg-functions-intro`**
2. En la lista de recursos verás varios: la Function App, un plan de App Service y una **cuenta de almacenamiento** con un nombre autogenerado (empieza con letras minúsculas y números, ej: `stfnnorbeyi...`)
3. Haz clic en la cuenta de almacenamiento

### 2.3 Crear el contenedor

Dentro de la cuenta de almacenamiento:

1. En el menú lateral, haz clic en **"Contenedores"** (dentro de la sección Almacenamiento de datos)
2. Haz clic en **"+ Contenedor"**
3. En el campo **"Nombre"** escribe: `archivos-entrada`
4. En **"Nivel de acceso público"** deja **"Privado"** (sin acceso anónimo)
5. Haz clic en **"Crear"**

El contenedor aparece en la lista. Haz clic en su nombre **`archivos-entrada`** para abrirlo.

Al abrirlo es posible que aparezca un mensaje de error de permisos relacionado con Microsoft Entra ID. Si ocurre, mira la línea que dice **"Método de autenticación: Cuenta de usuario de Microsoft Entra"** y haz clic en el enlace **"Cambiar a la clave de acceso"** que aparece al lado. La vista se recarga y el contenedor queda accesible correctamente.

### 2.4 Crear la función Blob Trigger desde el portal

Regresa a la Function App (`fn-[tu-apellido]-intro`):

1. En el menú lateral, haz clic en **"Funciones"**
2. Haz clic en **"+ Crear"**
3. Haz clic en **"Crear en Azure Portal"**
4. En la lista de plantillas selecciona **"Azure Blob Storage trigger"**
5. Asigna el nombre: `ProcesarArchivo`
6. En el campo **"Ruta de acceso"** escribe: `archivos-entrada/{name}`
7. En **"Conexión de cuenta de almacenamiento"** selecciona **`AzureWebJobsStorage`** (ya está configurada automáticamente)
8. Haz clic en **"Crear"**

> **¿Qué significa `archivos-entrada/{name}`?**
> Es la ruta que Azure monitorea. `archivos-entrada` es el nombre del contenedor que creamos. `{name}` es un patrón que captura el nombre del archivo subido y lo pone disponible dentro del código como variable.

Haz clic en el nombre `ProcesarArchivo` y luego en **"Código y prueba"**.

### 2.5 El código generado por el portal

```javascript
module.exports = async function (context, myBlob) {
    context.log("JavaScript blob trigger function processed blob \n Name:", context.bindingData.name, "\n Blob Size:", myBlob.length, "Bytes");
};
```

> **¿Qué hace este código?**
> Recibe `myBlob` con el contenido binario del archivo y `context.bindingData.name` con el nombre del archivo que activó la función. El log muestra el nombre y el tamaño en bytes.

### 2.6 Personalizar el código

Reemplaza el contenido por el siguiente código y haz clic en **"Guardar"**:

```javascript
module.exports = async function (context, myBlob) {
    const nombre = context.bindingData.name;
    const tamanio = myBlob.length;
    const extension = nombre.split('.').pop().toLowerCase();

    // Construir información del archivo procesado
    const info = {
        archivo: nombre,
        extension: extension,
        tamanioBytes: tamanio,
        tamanioKB: (tamanio / 1024).toFixed(2),
        procesadoEn: new Date().toISOString(),
        contenedor: 'archivos-entrada',
    };

    context.log('Archivo detectado y procesado:');
    context.log(JSON.stringify(info, null, 2));

    // En una aplicación real aquí iría la lógica de procesamiento:
    // - Leer el contenido del archivo: myBlob.toString('utf8')
    // - Guardar en base de datos
    // - Enviar notificación
    // - Transformar el archivo
};
```

> **¿Qué hace esta versión?**
> Extrae el nombre, la extensión y el tamaño del archivo. Construye un objeto JSON con esa información y lo escribe en el log. El comentario final indica dónde iría la lógica real de procesamiento en un proyecto verdadero.

### 2.7 Subir un archivo para probar

Regresa a la cuenta de almacenamiento en el portal:

1. Ve a **"Contenedores"** → haz clic en **`archivos-entrada`**
2. Haz clic en **"Cargar"** en la barra superior
3. Selecciona cualquier archivo de tu equipo (un `.txt`, `.csv`, `.png` o cualquier otro)
4. Haz clic en **"Cargar"**

El archivo aparece en la lista del contenedor. Azure detecta la carga y activa la función automáticamente.

### 2.8 Verificar la ejecución en los logs

Regresa a la Function App → `ProcesarArchivo` → **"Código y prueba"** → **"Registros"**.

En unos segundos deben aparecer los logs con la información del archivo:

```
Archivo detectado y procesado:
{
  "archivo": "mi-documento.txt",
  "extension": "txt",
  "tamanioBytes": 1024,
  "tamanioKB": "1.00",
  "procesadoEn": "2026-08-10T14:30:00.000Z",
  "contenedor": "archivos-entrada"
}
```

> El tiempo entre la carga del archivo y la ejecución de la función suele ser de unos segundos, pero en el plan de consumo puede tardar hasta 1 minuto si la función estaba en reposo (cold start).

Prueba subiendo archivos de distintos tipos y tamaños, y observa cómo los logs reflejan cada uno.

## Resumen: los tres triggers vistos en el curso

| Trigger | ¿Cuándo se ejecuta? | ¿Quién lo activa? | Devuelve respuesta? |
|---|---|---|---|
| HTTP | Al recibir una petición web | Un cliente (navegador, Postman, API) | Sí |
| Timer | Según un horario NCRONTAB | Azure automáticamente | No |
| Blob Storage | Al subir o modificar un archivo | Una carga a Blob Storage | No |

Los tres comparten la misma característica serverless: escala a cero cuando no hay eventos, se activan solos cuando los hay, y se paga solo por las ejecuciones reales.

---

## Relación con lo visto en el curso

El Blob Storage trigger conecta directamente con los servicios de almacenamiento que el grupo de Storage presentó. Un flujo real podría ser:

```
Usuario sube archivo a Blob Storage (nivel Hot)
            ↓
  Blob trigger activa la Function
            ↓
  La Function lee el archivo, lo procesa
  y mueve el resultado a otro contenedor
  o guarda metadatos en una base de datos
```

Este patrón es uno de los más comunes en arquitecturas cloud: desacoplar la carga del archivo de su procesamiento mediante un evento. Quien sube el archivo no espera a que se procese; la Function lo hace de forma asincrónica en cuanto Azure lo detecta.

## Solución de problemas frecuentes

| Problema | Causa | Solución |
|---|---|---|
| El Timer no aparece en los logs en el tiempo esperado | Cold start: la Function App estaba inactiva | Esperar hasta 2 ciclos completos; la primera ejecución puede retrasarse |
| El Blob trigger no se activa al subir el archivo | El nombre del contenedor en la ruta no coincide con el creado | Verificar que la ruta en `function.json` sea exactamente `archivos-entrada/{name}` |
| `context.bindingData.name` devuelve `undefined` | El patrón `{name}` no está en la ruta del trigger | Revisar en `function.json` que la ruta incluya `/{name}` al final |
| Los logs no aparecen en tiempo real | La conexión de logs del portal se desconectó | Hacer clic en el ícono de reconexión en la barra de logs o recargar la página |
| El archivo se sube pero la función da error 500 | Error en el código del handler | Revisar los logs completos para ver el mensaje de error exacto |
