## ¿Qué es Serverless?

A lo largo del curso hemos recorrido una progresión en la responsabilidad que asumimos sobre la infraestructura:

- En **IaaS** (VM) instalamos el SO, el runtime, el servidor web y la aplicación.
- En **PaaS** (App Service) solo subimos el código; Azure gestiona el resto.
- En **Serverless** ni siquiera pensamos en servidores: escribimos una función que responde a un evento, y Azure se encarga de todo lo demás.

La palabra "serverless" no significa que no haya servidores. Los hay, pero son completamente invisibles. No los aprovisionamos, no los configuramos, no los escalamos y no los pagamos cuando no se usan.

### Las características que definen Serverless

**Orientado a eventos.** El código no corre de forma continua. Se ejecuta en respuesta a un desencadenador (trigger): una petición HTTP, un mensaje en una cola, un archivo subido a Blob Storage, un temporizador, etc. Cuando no hay eventos, no hay ejecución.

**Escala automática hasta cero.** Si la función recibe una petición por mes, Azure ejecuta el código una vez. Si recibe un millón en un minuto, Azure escala horizontalmente de forma instantánea y automática. Cuando no hay peticiones, la escala baja a cero.

**Pago por ejecución.** En el plan de consumo se paga por el número de ejecuciones y el tiempo de cómputo consumido, no por tener un servidor encendido. Las primeras 400.000 GB-segundos y el primer millón de ejecuciones por mes son gratuitos en Azure.

### Cómo encaja en los modelos de servicio

| Aspecto | IaaS (VM) | PaaS (App Service) | Serverless (Functions) |
|---|---|---|---|
| SO y runtime | Nosotros | Azure | Azure |
| Servidor web | Nosotros | Azure | Azure |
| Escala | Manual | Automática configurable | Automática hasta cero |
| Pago | Por hora encendida | Por plan mensual | Por ejecución |
| Estado | Siempre activo | Siempre activo | Solo cuando hay evento |
| Ideal para | Control total del entorno | Apps web siempre en línea | Código en respuesta a eventos |

## ¿Qué son Azure Functions?

Azure Functions es la implementación de Serverless de Microsoft Azure. Permite escribir pequeñas unidades de código (funciones) que se ejecutan en respuesta a distintos tipos de eventos.

### Tipos de trigger disponibles

| Trigger | Cuándo se ejecuta |
|---|---|
| HTTP | Al recibir una petición web (GET, POST, etc.) |
| Timer | En un horario definido (como un cron) |
| Blob Storage | Cuando se sube o modifica un archivo |
| Queue Storage | Cuando llega un mensaje a una cola |
| Event Grid | Al ocurrir un evento en Azure |
| Cosmos DB | Cuando cambian datos en la base de datos |

En esta guía usamos el trigger **HTTP**, que es el más intuitivo para empezar: la función responde como si fuera un endpoint de una API.

### Planes de hospedaje

El **plan de consumo** es el que usaremos. Azure gestiona toda la infraestructura, la función escala sola y se paga por uso. Es el más económico para cargas intermitentes y el que mejor ilustra el concepto serverless.

## Parte 1: Crear la Function App en el portal

Una **Function App** es el contenedor que agrupa una o más funciones. Comparten el plan de hospedaje, el runtime y la configuración.

### 1.1 Acceder al portal

Abre [portal.azure.com](https://portal.azure.com) e inicia sesión con tu cuenta Azure for Students.

### 1.2 Crear el recurso

1. En la barra de búsqueda escribe **`Function App`**
2. Selecciona **Aplicación de funciones** en los resultados
3. Haz clic en **+ Crear**

### 1.3 Configurar la Function App

Completa los campos con estos valores:

| Campo | Valor |
|---|---|
| **Suscripción** | Azure for Students |
| **Grupo de recursos** | Crear nuevo → `rg-functions-intro` |
| **Nombre de la aplicación de funciones** | Un nombre único, ej: `fn-[tu-apellido]-intro` |
| **¿Desea implementar código o una imagen de contenedor?** | Código |
| **Pila de runtime** | Node.js |
| **Versión** | 20 LTS |
| **Región** | East US |
| **Sistema operativo** | Linux |
| **Plan de hospedaje** | **Plan de consumo (Serverless)** |

> El Plan de consumo es el que activa la facturación por ejecución y el escalado a cero. Es fundamental seleccionarlo para experimentar el comportamiento verdaderamente serverless.

### 1.4 Crear el recurso

1. Haz clic en **Revisar y crear**
2. Verifica que el plan sea **Consumo (Serverless)**
3. Haz clic en **Crear**

Azure tardará entre 1 y 2 minutos en aprovisionar la Function App. Cuando aparezca "La implementación se completó", haz clic en **Ir al recurso**.

## Parte 2: Crear la primera función

### 2.1 Agregar una función HTTP

Dentro de la Function App, la pantalla de bienvenida muestra tres opciones de entorno de desarrollo.

1. Haz clic en el botón azul **"Crear en Azure Portal"** — es la opción del centro de la pantalla de bienvenida.

Se abre un panel lateral a la derecha con las plantillas disponibles:

2. Selecciona **"HTTP trigger"** en la lista de plantillas.
3. En el campo **"Nombre de la función"** escribe: `SaludarHttp`
4. En **"Nivel de autorización"** selecciona **`Anonymous`** — así cualquiera puede llamarla sin clave de API.
5. Haz clic en el botón **"Crear"** al final del panel.

Cuando la función se cree, aparece en la lista de funciones de la aplicación:

6. Haz clic en el nombre **"SaludarHttp"** para abrirla.

Ya dentro de la función, en el menú lateral izquierdo:

7. Haz clic en **"Código y prueba"** — ahí está el editor con el código JavaScript de la función.

### 2.2 Explorar el código generado

Azure genera automáticamente el código inicial. Haz clic en **"Código y prueba"** en el menú lateral de la función para verlo.

El archivo `index.js` generado tiene una estructura similar a esta:

```javascript
module.exports = async function (context, req) {
    context.log('JavaScript HTTP trigger function processed a request.');

    const name = (req.query.name || (req.body && req.body.name));
    const responseMessage = name
        ? "Hello, " + name + ". This HTTP triggered function executed successfully."
        : "This HTTP triggered function executed successfully. Pass a name in the query string or in the request body for a personalized response.";

    context.res = {
        // status: 200, /* Defaults to 200 */
        body: responseMessage
    };
}
```

> **¿Qué hace este código?**
> La función recibe `context` (para logs y respuesta) y `req` (la petición). Busca el parámetro `name` primero en la query string (`req.query.name`) y luego en el body (`req.body.name`). Si lo encuentra devuelve un saludo personalizado; si no, un mensaje genérico. El status 200 está comentado porque es el valor por defecto.

> **Nota sobre el modelo de programación:** el portal genera código con el modelo v3 de Azure Functions (`module.exports`), que no necesita instalar ningún paquete externo. Existe también el modelo v4 (`const { app } = require('@azure/functions')`), más moderno, pero requiere instalar dependencias vía npm y no funciona directamente en el editor del portal.

## Parte 3: Modificar la función

Vamos a personalizar el código para que haga algo más interesante. Reemplaza el contenido del archivo por el siguiente código:

```javascript
module.exports = async function (context, req) {

    // Leer el parámetro 'nombre' de la URL (?nombre=Juan)
    const nombre = req.query.nombre || 'visitante';

    // Construir la respuesta con información del entorno
    const respuesta = {
        mensaje: `Hola, ${nombre}! Esta respuesta viene de una Azure Function.`,
        modelo: 'Serverless (Plan de consumo)',
        timestamp: new Date().toISOString(),
        url: req.originalUrl,
    };

    // Devolver la respuesta como JSON
    context.res = {
        status: 200,
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(respuesta)
    };
};
```

Haz clic en **"Guardar"** en la barra superior del editor.

> **¿Qué hace esta versión?**
> Ahora la función lee el parámetro `nombre` de la URL, construye un objeto JSON con el saludo, el modelo de servicio y el timestamp, y lo devuelve como respuesta. El cliente recibe JSON en lugar de texto plano, que es el formato estándar de una API.

## Parte 4: Probar la función

### 4.1 Probar desde el portal

Dentro de la vista "Código y prueba":

1. Haz clic en **"Probar/Ejecutar"** en la barra superior
2. En el panel que se abre, selecciona el método **GET**
3. En la sección **"Parámetros de consulta"**, agrega:
   - Clave: `nombre`
   - Valor: `[tu nombre]`
4. Haz clic en **"Ejecutar"**
5. En el panel de respuesta verás el JSON generado por la función

### 4.2 Obtener la URL pública

1. En el menú lateral de la función, haz clic en **"Obtener la dirección URL de la función"**
2. Copia la URL que aparece. Tendrá un formato similar a:

```
https://fn-[tu-apellido]-intro.azurewebsites.net/api/SaludarHttp
```
3. No olvides habilitar la función en el panel superior.

### 4.3 Probar desde el navegador

Abre el navegador y pega la URL con el parámetro de nombre:

```
https://fn-[tu-apellido]-intro.azurewebsites.net/api/SaludarHttp?nombre=Juan
```

Debes ver la respuesta JSON directamente en el navegador:

```json
{
  "mensaje": "Hola, Juan! Esta respuesta viene de una Azure Function.",
  "modelo": "Serverless (Plan de consumo)",
  "timestamp": "2026-08-09T14:30:00.000Z",
  "url": "https://fn-[tu-apellido]-intro.azurewebsites.net/api/SaludarHttp?nombre=Juan"
}
```

### 4.4 Probar con Postman

1. Método: **GET**
2. URL: la misma con el parámetro `?nombre=[tu nombre]`
3. No se necesita ningún header ni body adicional

Prueba también sin el parámetro:

```
https://fn-[tu-apellido]-intro.azurewebsites.net/api/SaludarHttp
```

Debes ver `"mensaje": "Hola, visitante! ..."`, confirmando que el valor por defecto funciona.

## Parte 5: Observar el comportamiento Serverless

### 5.1 Consultar las métricas de ejecución

1. En la Function App (no en la función individual), ve al menú lateral → **"Métricas"**
2. Selecciona la métrica **"Recuento de ejecuciones de funciones"**
3. Verás una gráfica con los picos de ejecución cuando hiciste las pruebas

### 5.2 Consultar los logs en tiempo real

Desde la vista "Código y prueba" de la función:

1. Haz clic en **"Registros"** en la parte inferior del editor
2. Abre el navegador o Postman y llama a la función varias veces
3. Observa cómo aparecen los mensajes del `context.log(...)` en tiempo real

Estos logs muestran exactamente cuándo y cuántas veces se ejecutó la función, algo que en una VM habría que configurar manualmente con herramientas adicionales.

## ¿Qué acabamos de hacer?

Desplegamos un endpoint HTTP que:

- No tiene servidor encendido de forma permanente
- Responde a peticiones en milisegundos
- Escala automáticamente si lo llaman miles de veces simultáneamente
- Cuesta cero mientras no se ejecuta

Y para lograrlo, solo escribimos código. No creamos VMs, no instalamos Node.js, no configuramos nginx, no abrimos puertos en un NSG. Azure gestionó todo eso de forma invisible.

## Solución de problemas frecuentes

| Problema | Causa | Solución |
|---|---|---|
| La función devuelve error 500 | El código usa `require('@azure/functions')` (modelo v4) pero el entorno del portal no tiene el paquete instalado | Reemplazar el código por el modelo v3: `module.exports = async function (context, req) {...}` |
| La URL devuelve 401 Unauthorized | La función tiene nivel de autorización distinto de Anonymous | Verificar que el nivel sea `anonymous` en el código y en la configuración |
| La URL devuelve 404 | El nombre de la función en el código no coincide con el nombre del archivo | Verificar que `app.http('SaludarHttp', ...)` use exactamente el nombre de la función creada |
| Los cambios en el editor no se reflejan | El archivo no fue guardado | Hacer clic en "Guardar" antes de probar |
| El JSON devuelto no tiene formato | El navegador no formatea JSON automáticamente | Instalar una extensión de navegador para visualizar JSON, o usar Postman |
| La primera petición tarda varios segundos | Cold start: la función arranca desde cero tras inactividad | Es el comportamiento esperado en el plan de consumo; las siguientes peticiones son más rápidas |
