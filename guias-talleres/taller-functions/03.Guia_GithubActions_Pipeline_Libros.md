# Pipeline CI/CD con GitHub Actions
## De un push en GitHub a un contenedor corriendo en Azure, con PostgreSQL administrado

**Computación en la nube**

---

## ¿Qué vamos a construir?

En la guía de Docker en VMs, el flujo de actualizar la API era manual: copiar archivos con `scp`, conectarse por SSH, reconstruir la imagen con `docker build`, detener el contenedor viejo y correr el nuevo. Cada cambio de código significaba repetir esos pasos a mano.

En esta guía automatizamos exactamente eso. El flujo final será:

```
Editas código en tu equipo
        │
        │  git push
        ▼
   GitHub recibe el push
        │
        │  dispara el workflow automáticamente
        ▼
GitHub Actions:
  1. Construye la imagen Docker
  2. La sube a Azure Container Registry (ACR)
  3. Despliega un contenedor en Azure Container Instances (ACI)
        │
        ▼
La API queda corriendo con una URL pública,
conectada a PostgreSQL administrado por Azure
```

Nadie se conecta por SSH. Nadie ejecuta `docker build` a mano. Un `git push` dispara todo el proceso.

---

## Qué es CI/CD y cuándo ocurre cada parte

**CI (Integración Continua):** cada vez que se sube código nuevo, un proceso automático lo construye y verifica. En nuestro caso, "construir" es `docker build`. No hay tests automatizados en esta guía, pero en un proyecto real esta etapa también correría pruebas antes de continuar.

**CD (Despliegue Continuo):** si la construcción fue exitosa, el sistema despliega automáticamente la nueva versión a un entorno. En nuestro caso, eso es actualizar el contenedor en ACI con la imagen recién construida.

**¿Cuándo ocurre?** El disparador (trigger) de este pipeline es un `push` a la rama `main` del repositorio. Desde el momento en que GitHub recibe ese push, corre sin que nadie más intervenga: construye, sube la imagen y despliega. Esto reemplaza por completo la secuencia manual `scp` → `ssh` → `docker build` → `docker run` que hicimos antes.

## Parte 1: Crear Azure Database for PostgreSQL (servicio administrado)

Hasta ahora instalamos PostgreSQL manualmente en una VM. Ahora usamos el servicio administrado: Azure se encarga del motor, los parches, los backups y la disponibilidad. Nosotros solo gestionamos el esquema y los datos — es exactamente la diferencia IaaS vs PaaS que vimos en las presentaciones de bases de datos.

### 1.1 Crear el recurso

1. En el portal de Azure, busca **`Azure Database for PostgreSQL`**
2. Haz clic en **"+ Crear"**
3. Selecciona **"Servidor flexible"** (Flexible Server)

### 1.2 Configurar el servidor

| Campo | Valor |
|---|---|
| **Suscripción** | Azure for Students |
| **Grupo de recursos** | Crear nuevo → `rg-pipeline-libros` |
| **Nombre del servidor** | `pg-[tu-apellido]-libros` |
| **Región** | East US |
| **Versión de PostgreSQL** | 16 |
| **Opción de cómputo + almacenamiento** | Burstable → Standard_B1ms |
| **Método de autenticación** | Autenticación de PostgreSQL |
| **Nombre de usuario administrador** | `apiuser` |
| **Contraseña** | Elige una contraseña segura y anótala |

### 1.3 Configurar redes

En la pestaña **"Redes"**:

| Campo | Valor |
|---|---|
| **Método de conectividad** | Acceso público (direcciones IP permitidas) |
| **Permitir acceso público** | Marcar la casilla |
| **Reglas de firewall** | Marcar **"Permitir acceso público desde cualquier servicio de Azure dentro de Azure a este servidor"** |

> Esta regla permite que ACI (donde correrá el contenedor) se conecte al servidor sin configurar una IP fija. En un entorno de producción real se restringiría a rangos de IP específicos.

### 1.4 Crear el recurso

Haz clic en **"Revisar y crear"** → **"Crear"**. Tarda entre 5 y 10 minutos en aprovisionarse.

### 1.5 Crear la base de datos y el esquema

Cuando el servidor esté listo, conéctate desde tu equipo con `psql` (o desde Azure Cloud Shell si prefieres no instalar nada):

```bash
psql "host=pg-[tu-apellido]-libros.postgres.database.azure.com port=5432 dbname=postgres user=apiuser password=[tu-contraseña] sslmode=require"
```

Dentro de `psql`, crea la base de datos y otorga permisos:

```sql
CREATE DATABASE libros_db;
\c libros_db
GRANT ALL ON SCHEMA public TO apiuser;
\q
```

> Recuerda el fix que ya conocemos: PostgreSQL 15+ requiere el `GRANT` explícito sobre el esquema `public`. Sin este paso, Sequelize se conecta pero falla al crear la tabla.

### 1.6 Habilitar SSL en la conexión de Sequelize

Azure Database for PostgreSQL Flexible Server **requiere SSL** en todas las conexiones por defecto. El código de Sequelize que usamos hasta ahora (con PostgreSQL en una VM) no lo necesitaba, porque ahí la conexión no forzaba cifrado. Con el servicio administrado sí es obligatorio.

Abre `src/config/database.js` y agrega el bloque `dialectOptions`:

```javascript
const { Sequelize } = require('sequelize');

const sequelize = new Sequelize(
  process.env.DB_NAME,
  process.env.DB_USER,
  process.env.DB_PASSWORD,
  {
    host: process.env.DB_HOST,
    port: process.env.DB_PORT || 5432,
    dialect: 'postgres',
    dialectOptions: {
      ssl: {
        require: true,
        rejectUnauthorized: false
      }
    },
    logging: false,
  }
);

module.exports = sequelize;
```

> **`require: true`** obliga a la conexión a usar SSL; sin este bloque, Sequelize intenta conectarse en texto plano y el servidor la rechaza con el error `no pg_hba.conf entry ... no encryption`. **`rejectUnauthorized: false`** evita que Node.js rechace el certificado de Azure por no venir de una autoridad certificadora reconocida localmente — es una configuración estándar al conectarse a servicios administrados en la nube.

Guarda el cambio y haz commit — lo subiremos junto con el resto del código en la Parte 5.

### 1.7 Anotar el endpoint de conexión

El host de tu servidor es:

```
pg-[tu-apellido]-libros.postgres.database.azure.com
```

Lo usarás como `DB_HOST` en la configuración del contenedor.

## Parte 2: Crear Azure Container Registry (ACR)

ACR es un registro privado de imágenes Docker. En las guías anteriores usábamos imágenes públicas de Docker Hub (`node:20-alpine`, `postgres:16-alpine`); ahora vamos a publicar nuestra **propia** imagen en un registro privado, como se hace en cualquier empresa.

### 2.1 Crear el recurso

1. En el portal de Azure, busca **`Azure Container Registry`**
2. Haz clic en **"+ Crear"**

### 2.2 Configurar el registro

| Campo | Valor |
|---|---|
| **Suscripción** | Azure for Students |
| **Grupo de recursos** | `rg-pipeline-libros` (el mismo de PostgreSQL) |
| **Nombre del registro** | `acr[tuapellido]libros` (sin guiones, solo letras y números) |
| **Ubicación** | East US |
| **Plan de precios** | Básico |
| **Modo de permisos de asignación de roles** | Dejar la opción por defecto: **"Permisos del Registro RBAC"** |

> La opción alternativa ("Permisos del registro RBAC + repositorio ABAC") habilita permisos diferenciados por repositorio individual dentro del registro — útil en empresas con decenas de imágenes y equipos distintos. Con un solo registro y una sola imagen (`api-libros`), la opción por defecto es suficiente.

Haz clic en **"Revisar y crear"** → **"Crear"**.

### 2.3 Habilitar el usuario administrador

GitHub Actions necesita credenciales para hacer push de imágenes al registro.

1. Ve al recurso ACR recién creado
2. En el menú lateral, haz clic en **"Configuración"** → **"Claves de acceso"**
3. Activa el interruptor **"Usuario administrador"**
4. Anota los tres valores que aparecen:
   - **Servidor de inicio de sesión** (ej: `acrnorbeylibros.azurecr.io`)
   - **Nombre de usuario**
   - **contraseña**

Los necesitarás en el siguiente paso.

## Parte 3: Configurar Secrets en GitHub

Las credenciales de Azure nunca van escritas en el código ni en el workflow. Se guardan como **Secrets** en la configuración del repositorio, y GitHub Actions los inyecta de forma segura durante la ejecución.

### 3.1 Ir a la configuración del repositorio

1. Abre tu repositorio en GitHub
2. Ve a **"Settings"** → **"Secrets and variables"** → **"Actions"**
3. Haz clic en **"New repository secret"**

### 3.2 Crear los secrets necesarios

Crea uno por uno los siguientes secrets con los valores que anotaste en las partes anteriores:

| Nombre del secret | Valor |
|---|---|
| `ACR_LOGIN_SERVER` | El "Servidor de inicio de sesión" de ACR (ej: `acrnorbeylibros.azurecr.io`) |
| `ACR_USERNAME` | El nombre de usuario de ACR |
| `ACR_PASSWORD` | La contraseña de ACR |
| `DB_HOST` | El host de PostgreSQL (ej: `pg-norbey-libros.postgres.database.azure.com`) |
| `DB_PASSWORD` | La contraseña que definiste para `apiuser` |
| `AZURE_CREDENTIALS` | Ver paso 3.3 |

### 3.3 Crear las credenciales de Azure para el despliegue

GitHub Actions necesita autenticarse contra Azure para poder crear el contenedor en ACI. Se hace con un **Service Principal**.

Abre **Azure Cloud Shell** (ícono `>_` en el portal) y ejecuta:

```bash
az ad sp create-for-rbac \
  --name "sp-pipeline-libros" \
  --role contributor \
  --scopes /subscriptions/$(az account show --query id -o tsv)/resourceGroups/rg-pipeline-libros \
  --sdk-auth
```

El comando devuelve un bloque JSON similar a:

```json
{
  "clientId": "...",
  "clientSecret": "...",
  "subscriptionId": "...",
  "tenantId": "..."
}
```

Copia **todo el bloque JSON completo** (incluyendo las llaves `{ }`) y pégalo como valor del secret `AZURE_CREDENTIALS` en GitHub.

> **¿Qué es un Service Principal?** Es una identidad que representa a una aplicación (en este caso, el pipeline de GitHub Actions) en lugar de a un usuario humano. Tiene permisos limitados al grupo de recursos indicado (`--scopes`), siguiendo el principio de menor privilegio: el pipeline solo puede actuar dentro de `rg-pipeline-libros`, no en toda la suscripción.

## Parte 4: El workflow de GitHub Actions

### 4.1 Crear la carpeta y el archivo del workflow

En la raíz de tu repositorio, crea la siguiente estructura:

```
mi-api-libros/
├── .github/
│   └── workflows/
│       └── deploy.yml
├── src/
├── index.js
├── package.json
└── Dockerfile
```

### 4.2 Escribir el workflow

Crea `deploy.yml` con el siguiente contenido:

```yaml
name: Deploy API Libros

# Se dispara cada vez que se hace push a la rama main
on:
  push:
    branches: [main]

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      # Paso 1: descarga el código del repositorio al runner de GitHub
      - name: Checkout del código
        uses: actions/checkout@v4

      # Paso 2: autentica contra Azure Container Registry
      - name: Login a ACR
        uses: azure/docker-login@v1
        with:
          login-server: ${{ secrets.ACR_LOGIN_SERVER }}
          username: ${{ secrets.ACR_USERNAME }}
          password: ${{ secrets.ACR_PASSWORD }}

      # Paso 3: construye la imagen y la sube a ACR
      # github.sha es el hash del commit — cada imagen queda etiquetada
      # con el commit exacto que la generó, para poder rastrearla
      - name: Build y push de la imagen
        run: |
          docker build -t ${{ secrets.ACR_LOGIN_SERVER }}/api-libros:${{ github.sha }} .
          docker push ${{ secrets.ACR_LOGIN_SERVER }}/api-libros:${{ github.sha }}

  deploy:
    # Este job solo corre si build-and-push terminó exitosamente
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      # Autenticación contra Azure usando el Service Principal
      - name: Login a Azure
        uses: azure/login@v1
        with:
          creds: ${{ secrets.AZURE_CREDENTIALS }}

      # Despliega (o actualiza) el contenedor en Azure Container Instances
      - name: Deploy a Container Instances
        uses: azure/aci-deploy@v1
        with:
          resource-group: rg-pipeline-libros
          dns-name-label: api-libros-${{ github.repository_owner }}
          image: ${{ secrets.ACR_LOGIN_SERVER }}/api-libros:${{ github.sha }}
          registry-login-server: ${{ secrets.ACR_LOGIN_SERVER }}
          registry-username: ${{ secrets.ACR_USERNAME }}
          registry-password: ${{ secrets.ACR_PASSWORD }}
          name: aci-api-libros
          location: eastus
          ports: 3000
          environment-variables: |
            DB_HOST=${{ secrets.DB_HOST }}
            DB_PORT=5432
            DB_NAME=libros_db
            DB_USER=apiuser
            PORT=3000
          secure-environment-variables: |
            DB_PASSWORD=${{ secrets.DB_PASSWORD }}
```

> **¿Por qué dos jobs separados (`build-and-push` y `deploy`)?** Separar la construcción del despliegue es una buena práctica: si el build falla, el despliegue nunca se intenta gracias a `needs: build-and-push`. También permite ver claramente en el historial de Actions cuál de las dos etapas falló si algo sale mal.

> **`secure-environment-variables`:** a diferencia de `environment-variables`, este campo oculta el valor en los logs de ejecución y en el panel de ACI. Se usa para credenciales como `DB_PASSWORD`, que nunca deben aparecer en texto plano en ningún log.

### 4.3 Confirmar el Dockerfile

Verifica que tu `Dockerfile` (de la guía de PostgreSQL con Sequelize) esté en la raíz del repositorio:

```dockerfile
FROM node:20-alpine

WORKDIR /app

COPY package.json ./
RUN npm install --omit=dev

COPY index.js ./
COPY src/ ./src/

EXPOSE 3000

CMD ["node", "index.js"]
```

Este es el mismo Dockerfile que ya construyeron; no necesita cambios para funcionar con el pipeline.

## Parte 5: Disparar el pipeline

### 5.0 Registrar el proveedor de Container Instances (una sola vez por suscripción)

Si es la primera vez que se usa Azure Container Instances en esta suscripción, el proveedor de recursos correspondiente no está activado por defecto. Sin este paso, el job `deploy` falla con el error `The subscription is not registered to use namespace 'Microsoft.ContainerInstance'`.

Desde **Azure Cloud Shell** (ícono `>_` en el portal):

```bash
az provider register --namespace Microsoft.ContainerInstance
```

Verifica que quedó activo (puede tardar hasta 3 minutos):

```bash
az provider show --namespace Microsoft.ContainerInstance --query registrationState
```

Debe devolver `"Registered"`. Este registro se hace una sola vez por suscripción — no hay que repetirlo en despliegues futuros.

### 5.1 Hacer commit y push

Desde tu terminal, en la carpeta del proyecto:

```bash
git add .
git commit -m "Agregar pipeline de CI/CD con GitHub Actions"
git push origin main
```

En el momento del push, el workflow se dispara automáticamente.

### 5.2 Observar la ejecución

1. Ve a tu repositorio en GitHub
2. Haz clic en la pestaña **"Actions"**
3. Verás la ejecución en curso, con los dos jobs (`build-and-push` y `deploy`)
4. Haz clic en la ejecución para ver el detalle de cada paso en tiempo real

La primera ejecución tarda entre 3 y 6 minutos: construir la imagen desde cero, subirla a ACR y crear el contenedor en ACI.

### 5.3 Verificar el resultado en el portal

Cuando el workflow termine con el ícono verde ✓:

1. Ve al portal de Azure → grupo de recursos `rg-pipeline-libros`
2. Verás el recurso **`aci-api-libros`** (Container Instances)
3. Haz clic en él → **"Información general"**
4. Copia el **"FQDN"** (nombre de dominio completo), tendrá un formato como:

```
api-libros-[tu-usuario].eastus.azurecontainer.io
```

|---|---|---|

Este es el momento que demuestra todo el propósito de la guía.


## Resumen: lo manual vs lo automatizado

| Tarea | Antes (VM + Docker manual) | Ahora (GitHub Actions) |
|---|---|---|
| Copiar código a Azure | `scp` manual | `git push` |
| Construir la imagen | `docker build` por SSH | Automático en el runner de GitHub |
| Publicar la imagen | No existía (imagen local en la VM) | Push a ACR |
| Desplegar el contenedor | `docker run` manual | Automático vía `azure/aci-deploy` |
| Repetir en cada cambio | Todos los pasos anteriores, a mano | Un solo `git push` |
| Base de datos | PostgreSQL instalado manualmente en VM2 | Azure Database for PostgreSQL (administrado) |

## Solución de problemas frecuentes

| Problema | Causa | Solución |
|---|---|---|
| El job `build-and-push` falla en el login a ACR | Los secrets `ACR_*` tienen valores incorrectos | Verificar en ACR → Claves de acceso que el usuario administrador esté habilitado y copiar los valores exactos |
| `The subscription is not registered to use namespace 'Microsoft.ContainerInstance'` | El resource provider de ACI no está activado en la suscripción | Ejecutar `az provider register --namespace Microsoft.ContainerInstance` en Cloud Shell, esperar a que quede "Registered" y volver a ejecutar el workflow con "Re-run all jobs" |
| El job `deploy` falla con error de autorización | El `AZURE_CREDENTIALS` no tiene permisos sobre el grupo de recursos | Verificar que el Service Principal se creó con `--scopes` apuntando a `rg-pipeline-libros` |
| El contenedor se crea pero no responde | La API falla al conectarse a PostgreSQL | Ver los logs del contenedor en el portal: ACI → Contenedores → Registros |
| `no pg_hba.conf entry for host "...", no encryption` en los logs de ACI | Falta el bloque `dialectOptions.ssl` en `database.js` — Azure Database for PostgreSQL exige SSL y Sequelize está conectando en texto plano | Agregar `dialectOptions: { ssl: { require: true, rejectUnauthorized: false } }` según el paso 1.6, hacer commit y push |
| `permission denied for schema public` en los logs de ACI | No se ejecutó el GRANT sobre el esquema public en el servidor administrado | Repetir el paso 1.5 conectándose por `psql` |
| El FQDN no responde desde el navegador | El firewall del servidor PostgreSQL bloquea la conexión desde ACI | Verificar en el servidor PostgreSQL → Redes que esté marcada la opción "Permitir acceso desde servicios de Azure" |
| Cada push crea un contenedor nuevo con nombre distinto | El `name` en `aci-deploy` no es fijo o el DNS label cambia | Verificar que `name: aci-api-libros` y `dns-name-label` sean valores fijos, no dependientes de `github.sha` |
